Implementation comparison and qualification

Compare implementation stages without combining unrelated evidence.

Reference scope

This reference describes the Ledger 8 typed target and checked-effect pilot. It is an architectural reference, not a status report for the later Ledger 9 implementation. The compositional recording chapter explains the pilot's subsequent integration; the migration chapter explains the protocol changes.

Qualification by capability

Native Rust execution

  • Implementation cutoff: test(rust): gate rejected Rust constructs and witness secrecy .
  • 128 generated sources; 410 workspace test/doc-test groups passed.
  • All 37 top-level oracle sources ran through the new path, plus selected tiny, election, Zerocash and passport flows.
  • No first-class proof/deployment pipeline; the wrapper forced --skip-zk.

Recorded target and transaction preparation

  • Qualified at ci(rust): bound Linux validation artifact storage .
  • 217 sources, 196 compiled roots and 755 exports: 386 proof-required and 369 non-proof exports. Availability is not proof execution.
  • Sampled 37-source / 203-row behavior.
  • Selected original four Coracle plus seven microDAO proof selectors, with three explicitly balancing-disabled smoke selectors.
  • Ten required remote workflows passed at the final revision.
  • No crates.io release, Windows certification or universal parity claim.

Generated consumers and application cohorts

  • Qualified implementation test(rust): create fresh relation key directories ; closure docs(rust): close the 0.3.0 engineering milestone .
  • 19/19 required outcomes; 93 criteria; 121 supporting ADRs.
  • 198 roots, 232 inputs and 1,055 functions classified.
  • Runtime changed-line coverage 97.87%; mapped total 88.03%; testkit 97.62%; backend and macro cohorts retained separately at 95.11% and 100%.
  • DID v0.7.0: 12 stateful exports; 42 finite relation calls.
  • Passport cohort: 17 files, 75 pure exports, 202 behavior cases and four codec vectors. Full Passport ACC adoption was excluded after the construct inventory found no additional unique qualification mechanism; its exact composition remained unqualified.
  • Remote core: 742 cases in 63 result blocks at the named revision.
  • RustSec: zero vulnerability matches, with four workspace / three standalone notices and strict nonzero exit retained.

Counts overlap and must not be summed into one “tests passed” figure.

Checked-effect pilot and measured validation

At perf(test): shard historical laws in isolated processes , the pilot source includes the historical-test process sharding change. The full installed validation kept 974 unique planned and executed IDs with no failures, errors, skips or unrun cases. Four independent process shards reduced the measured wall time from 10,270 seconds (about 171 minutes) to 3,308 seconds (about 55 minutes), a 3.105× result on this frozen machine and source.

What remained unchanged matters more than the headline:

  • the original 940 cases and their assertions remained;
  • workers reconstructed independent temporary state;
  • live source/manifest mutation checks still ran;
  • original case IDs and accounting remained exact;
  • eight new corruption/source controls lived outside frozen discovery;
  • no validation result cache or live path cache was introduced.

It is a measured local optimization, not a universal CI speed claim.

Parity findings that changed the design

Comparison with TypeScript found Rust divergences, including incorrect hash-to-curve representation, the wrong Jubjub Schnorr predicate, permissive Boolean/bounded-unsigned decoding, and a validated-point alias that could panic for attacker-controlled coordinates.

The Rust comparison also exposed source/runtime defects: malformed native widths that JS silently sliced, and Merkle update underflow before a capacity check. Independent implementations made previously implicit assumptions observable in both directions.

Limits of the reference evidence

  • No formal proof of complete Compact semantics or universal TS parity.
  • Proof support is per applicable export and exact artifact set.
  • The pilot receipts do not establish final integration. The checked-effect integration records that subsequent stage.
  • Source locations at the pilot revision are owner locations plus structural paths, not complete nested ranges.
  • Aggregate decoded heap/object/CPU containment remains separate work.
  • Experimental WASM does not imply a production browser prover.
  • No Windows certification, package registry release or upstream adoption is implied by these scoped qualification results.
