Orientation

A contract crosses a boundary

Start with one state transition

A Compact contract is more than the text of a circuit. Its behavior includes the value returned, the ledger reads and writes, the witnesses called, the cost charged, the statement proved, and the transaction that eventually changes state. A second backend has to preserve those relationships.

Imagine a counter that increments and returns its new value. A generated Rust function can calculate the right number while recording the wrong ledger operation. A recorder can produce the right operations while preparing a proof for a different installed verifier. A valid proof can still fail a funded ledger application. Each of those failures occupies a different boundary.

Our journey began with a TypeScript-oriented Compact compiler and a Ledger 8 reference environment. The long-term question was whether Rust could become an ergonomic, typed way to use the same contract semantics. The answer emerged through repeated small deliveries rather than one replacement compiler.

What this book preserves

This edition follows the original Rust text emitter, the Rust AST rebuild, native execution, recorded execution, proof and wallet integration, the 0.3.0 closure, compositional effects, the functional Ledger 8 experiment, and the move to Ledger 9.

Every chapter asks four questions. What limitation triggered the work? Which owner changed? What behavior became possible? Which evidence established the result? A final section records what was still open at that point.

The commit explorer is the granular index. Phase assignments are editorial groupings over a frozen Git graph. Commit subjects are historical source material. They sometimes use shorthand or describe an intended result. The chapter narrative and its receipts supply the scope of acceptance.

Three ways to read

Read the chapters in order for the engineering story. Follow the Architecture link to walk a circuit through the pipeline. Use the Commit explorer to move from a milestone to its individual steps, then follow a published commit back to code.

The historical atlas preserves the earlier October documentation as an explicitly dated snapshot. The later chapters explain which earlier limitations were subsequently resolved.

The edition boundary

Released Compact 0.36.0 and the Ledger 9.1.0.1 SDK package matrix supply a separate interoperability reference. The local compatibility checkpoint used for this edition is v73 on November 13, 2026.

Why the distinctions matter

A guide becomes misleading when a reader cannot tell whether an example was merely generated, executed natively, proved, or applied to a ledger. This book keeps those stages visible. It also keeps historical Ledger 8 evidence useful while explaining the changed Ledger 9 SDK and representation contracts.

The objective remains faithful Compact behavior with useful Rust types, explicit diagnostics, and runtime checks where values cross an untrusted boundary.

Ledger 8 foundations

TypeScript and fixed ground

Why begin with the existing backend

The TypeScript path already connected Compact source to the ledger runtime and proof ecosystem. It provided generated contract interfaces, native host execution, witness callbacks, ledger operations, and the data used to construct proof statements. Reusing its behavior as a reference gave the Rust work something more precise than an aesthetic target.

Ledger 8 provided a stable package family. The compiler, on-chain VM, serialization, field arithmetic, cryptography and proof tooling could be pinned together. When a Rust state differed from a TypeScript state, the team could investigate the representation or operation instead of first reconciling two changing protocol generations.

The ledger stays authoritative

The Rust runtime reused the ledger's field, FAB alignment, state, VM, serialization and proof primitives. FAB is the aligned representation used to move values across these boundaries. A contract-level type can occupy several aligned atoms. Equal-looking host values do not establish identical serialized statements.

The counter example makes this concrete. A read should use the ledger operation and cost model for that slot. Replacing it with an independent Rust calculation could return the same number while missing the protocol's behavior.

What TypeScript captures taught us

Independent captures became a recurring technique. Generate a reference contract with a known compiler/runtime pair, execute selected calls, and retain the inputs, full state bytes, transcript, gas and expected refusal. Generated Rust then consumes the same scenario.

These captures are stronger than comparing a few printed values. They can detect a wrong state tag, an incorrect atom width, a reordered witness, a changed private transcript or a different gas path. They also need their own provenance. A capture generated by a mismatched runtime is an unreliable reference.

An important lineage correction

What was solved

A pinned reference made differential tests interpretable. The project could change the Rust architecture while retaining a stable account of source behavior and ledger representation.

What was still open

Reference captures cover named cases. They cannot establish whole-language equivalence by themselves. That gap later motivated capability inventories, source refusals, broader fixture matrices and proof/application gates.

TypeScript and Rust AST

Why add a Rust AST backend?

The Rust AST backend lets a Rust application call generated Compact code through types that preserve more of the contract’s meaning. A bounded integer carries its limit. A fixed Vector carries its element type and length. A circuit call consumes a context and returns the next one. These choices make several host-side mistakes visible while compiling the application.

The compiler also gains a structured way to build Rust. It checks a typed internal program, lowers admitted operations and constructs Rust syntax trees. That gives contributors explicit places to implement a language feature and diagnose unsupported cases.

The TypeScript backend supplies generated contract interfaces, witness callbacks, ledger access and proof data for JavaScript applications. It has typed declarations and runtime checks of its own. The comparison below follows the implementations and tests retained in the November 13, 2026 book edition.

This path fits applications already using Node.js, TypeScript and the existing JavaScript SDK integration.

Rust AST backend

Compact source
  → shared frontend checks
  → versioned typed IR
  → checked semantic lowering
  → structured Rust syntax
  → generated crate + typed runtime
  → ledger operations and proof inputs

The application imports generated Rust functions or contract wrappers. A call such as increment_by(context, amount) returns a Result containing the execution result and successor context.

This path fits Rust services and tools that need generated Compact APIs in the same language as their application.

Both paths begin with Compact’s frontend checks. Source typing and disclosure rules apply before host code is emitted. Rust’s generated interface adds checks at the application boundary, where developers supply arguments and connect calls.

Benefits for application developers

Keep contract meaning in the argument types

Consider the same Counter contract used in the walkthrough. Its amount parameter is Compact Uint<16>, which admits values from 0 through 65,535.

Surface Generated argument What the caller must supply
TypeScript bigint A bigint. The generated runtime checks the value’s range.
Rust AST BoundedUint<65535> A value constructed through the bounded carrier’s checked API. The function signature preserves that bound. 
let amount = BoundedUint::<65_535>::new(7)?;
let increment = increment_by(context, amount)?;

The Rust compiler refuses a plain u16 in this position. It also distinguishes carriers with different declared bounds. The integer’s value is checked when the bounded value is constructed. For example, new(65_536) returns an error.

TypeScript already rejects a number where the declaration expects bigint. Rust makes the contract’s bound part of the parameter type as well.

Make the state handoff explicit

A sequence of calls needs to continue from the returned context. The Rust call takes the context by value, so the compiler tracks which binding has been consumed.

let increment = increment_by(context, amount)?;
let reset = reset_round(increment.context)?;

Trying reset_round(context) after the increment produces E0382, “use of moved value.” In the TypeScript interface, the original and returned contexts have the same type and the caller selects which one to pass. Rust’s ownership rule catches reuse of that consumed binding before the application runs.

Build syntax as a tree

The Rust renderer constructs expressions, statements, blocks, paths and types using Rust syntax-tree libraries. The formatter renders those structures into readable source.

For example, a multiplication whose left operand is an addition is represented as a nested expression. Parentheses follow from that structure. A contributor can inspect the checked operation and the syntax node that represents it.

Give each semantic decision an owner

A feature crosses the source frontend, typed IR, validator, lowerer, renderer and runtime. Explicit boundaries make the responsibilities reviewable. Unsupported input can produce a diagnostic while its source and operation are still identifiable.

The checked operation model also supports composition. A read, assertion or write can appear inside a branch or sequence. A shared semantic fold handles admitted behavior through native and recorded adapters, reducing duplicated decisions about ordering and results.

Ledger 8 foundations

The first Rust emitter

The first useful proof of direction

The retained original Rust backend showed that Compact could produce useful Rust. Its Scheme passes operated on TypeScript-oriented compiler representations and assembled Rust source text. The original oracle's ancestry introduces the eight-file Ltypescript emitter in June 2026.

This was a practical implementation strategy. A compiler can reuse an already lowered representation and get a working target quickly. Generated crates and examples then make the missing operations visible.

Where text emission becomes expensive

Consider a nested expression containing a ledger read, a fallible conversion and a function call. A textual emitter must preserve the source type, track the updated context, arrange error propagation, and output legal Rust syntax. If those decisions share one string-building layer, a local feature can affect many unrelated cases.

A missing clone may become an ownership error. An extra conversion can change a value's admitted range. Parentheses can make syntactically legal code with the wrong grouping. Testing generated text catches some problems after emission, but the compiler still lacks a single closed place to decide whether a construct is valid for the target.

Why retain the original

The old backend supplied a valuable reference for the replacement. It contained behavior and generated-crate conventions that the new architecture had to preserve deliberately. Removing it would have discarded a comparative baseline precisely when the rebuild most needed one.

The project therefore used the original implementation as an oracle. The replacement could adopt a different internal design while comparing the external behavior of selected contracts.

The decision

Keep Scheme as the shared Compact frontend. Move target-specific semantic admission into a versioned internal model. Let a Rust backend construct Rust syntax through Rust syntax-tree libraries.

This change was about ownership of decisions. It did not require a new Compact language, a replacement ledger VM, or a parallel cryptographic specification.

Native AST milestone

A closed Rust boundary

The new pipeline

After shared Compact analysis, Chez Scheme lowered supported constructs into a versioned JSON model. Rust deserialized and checked that model, selected typed runtime operations, and built output through syn, quote, proc-macro2 and prettyplease.

The crucial word is supported. A closed internal representation gives each admitted node an explicit meaning. Unsupported constructs should produce a diagnostic at a known boundary. Silently manufacturing a placeholder would conceal a missing semantic case.

A vertical slice before a framework

The first slice used schema 1 for pure Field, Boolean, Unit, tuple and vector circuits, including Field addition. It explicitly refused ledger and witness constructs. Ledger-backed primitive types, Cell and Counter state changes, typed values and typed reads followed. Set, Map and List operations expanded that native surface. Pure conditionals, local bindings and circuit calls expanded the usable source subset.

Each slice joined several owners. Scheme supplied the source node and type. The Rust model represented it. Checked lowering established a legal operation. Syntax emission built the Rust expression. The runtime delegated ledger behavior to the VM. Generated consumers exercised the ordinary API.

Why structured syntax helped

A Rust syntax tree gives the emitter a representation for expressions, statements, blocks, paths and types. The formatter can render those nodes without encoding semantics in whitespace or string fragments.

That benefit has a boundary. Constructing an AST does not prove that the correct field operation or source conversion was chosen. The semantic checks still need to occur before rendering. The long-term architecture therefore pairs structured syntax with checked lowering.

The Milestone 1 result

The broad local native baseline closed at test(rust): gate rejected Rust constructs and witness secrecy . Publication followed at docs(site): pin the rewritten milestone implementation commit on October 2. Historical notes record 128 generated sources and 410 workspace test/doc-test groups.

The milestone used private IR schema 6 and runtime ABI 3. Its wrapper forced skip-zk. That is an essential scope boundary when reading the early success report.

What was solved

Compact could generate useful typed Rust that executed a supported contract subset natively through the ledger runtime. The compiler boundary became inspectable, and new source cases had named owners.

What was still open

Recording a transcript, preparing a call, generating a proof and applying a funded transaction were later deliveries. Native execution established an important foundation for them.

Recorded contracts milestone

Recording is an execution

A correct result still leaves a missing statement

A native function can return the expected value without retaining the operations needed for proof preparation. Re-running the function elsewhere also risks observing a different state or a different witness result.

The project introduced recorded execution as an explicit result. Execute against a context, retain the ordered ledger trace, and return both the native result and its recording. Replay then checks that the operations reproduce the expected public transition.

Replay gives a second check on the public transition. A reader can see both what the call returned and how it moved the ledger. The proof and funded transaction add their own checks later.

Give the ledger slot an owner

Typed field descriptors connect a source declaration to its physical ledger path. A CellSlot knows the value type and where the VM should read or write. Generated code supplies arguments and propagates the returned context.

That division prevents arbitrary path arithmetic from spreading across generated bodies. It also creates a reusable boundary for witness ledger views and public state inspection.

Keep procedural macros mechanical

Derive macros add representation rules for generated types. They can implement a checked cell codec or enum representation. A body-wide macro that interprets contract semantics would hide another compiler inside generated Rust.

The selected design uses a typed runtime DSL and narrow derives. The compiler owns the source program and its admitted operations. The runtime owns execution and representation primitives.

From a recording to a deployed operation

An observed call must bind the installed contract state and operation. The expected verifier belongs to that operation. Proof preparation needs to preserve that relationship when it constructs a statement.

Wallet-facing work added deployment and subsequent-call handoff, state observations, typed reads, and the metadata needed to build later calls from confirmed state. That made the generated API useful beyond isolated examples. A historical ABI 28 Counter observation recorded round advancing from 1 to 2. Indexed actions were bound to the final merged transaction hash and checked through a trusted node/indexer. That observation did not provide authenticated consensus finality.

Qualified consumers milestone

Closing 0.3.0

Why broaden the acceptance surface

A generated Counter is a useful vertical slice. Real users also need understandable generated APIs, compatibility checks, examples, diagnostics, package layout, application fixtures and proof consumers.

The 0.3.0 milestone brought those concerns into an explicit acceptance crosswalk. The team could then ask whether each promised outcome had code, tests, documentation and qualification evidence.

Real applications expose different pressure

DID and Passport exercised different application cohorts. DID covered twelve stateful exports with bounded native/recorded scenarios and proof receipts. The accepted Passport cohort covered 75 pure exports and had zero proof applicability. Together they exposed API and representation assumptions that a tiny circuit never touches.

Adoption was scoped. A proof-eligible selected export does not make every large contract cheap to prove. A partial contract exercise also needs to remain identified as such. Resource limits and the selected proof profile constrain what a local run establishes.

The importance of preserving a failed run

The closeout retained the original failed full run at revision test(rust): include child status in compatibility failures . Its final qualification joined the 423 successful unchanged-prefix commands with three recovery commands at the named source.

That is more informative than deleting failure evidence and showing a green badge. It explains which inputs and source remained valid, where repairs entered, and why the composite receipt was accepted.

ACC was explicitly removed from the 0.3.0 accepted scope after the construct inventory found no unique witness, struct or ledger mechanism requiring another qualification family. Its exact application composition remained unqualified. Decoder resource containment also had an explicit boundary, with broader aggregate containment left for follow-up.

A milestone can close responsibly when its agreed outcomes are satisfied and its excluded work is documented. Reopening the same accepted work without a new defect would slow the next milestone while adding little confidence.

Compositional recording

Shapes, operations and algebra

Before · Recognize the whole circuit

The early recorder worked like a set of templates. It inspected a circuit’s parameters, ledger actions and return value, then chose a recipe for a known pattern. The recipe could enforce the exact type and physical ledger slot. A different arrangement of familiar operations could still fail to find a recipe.

Mermaid source

Two shapes the old recorder knew

The Set insert comes from the historical oracle fixture. The Field example illustrates the saved-read pattern. Both excerpts omit their ledger declarations.

Shape What the recognizer looked for
Insert into an opaque-string Set One string parameter, exactly one insertion of that parameter into the declared Set slot, then a Unit result. A related membership shape expected no write and returned the membership Boolean.
Read an old Field value, update state and return the old value A root binding that reads a declared Field cell once, actions inside that binding, then a return of the saved Field value. 
// Shape 1 · The value inserted comes directly from the parameter.
export circuit addName(name: Opaque<"string">): [] {
  names.insert(disclose(name));
}

// Shape 2 · The result is the value from before the write.
export circuit replaceValue(next: Field): Field {
  const before = state.read();
  state.write(disclose(next));
  return before;
}

Here, a shape was a recognizer’s predicate over the existing circuit representation. The relevant entities were the circuit, its declarations, and the recording recipe selected by the recognizer. There was no common Shape object with child shapes that the compiler could assemble into a larger program.

After · Build a plan from typed operations

The replacement describes a circuit as an ordered plan. A block is a list of bindings plus a result. Each binding pairs an operation with a typed value and an IR location. A read produces a value other operations can use. A write updates a declared slot. An if operation contains two blocks. The validator checks both branches, including their result types, while execution takes only the selected branch.

Illustrative plans using the integrated operation model

addName(name: OpaqueString)

return Unit

replaceValue(next: Field)

before : Field = CellRead(state)
_      : Unit  = CellWrite(state, next)

The integrated model gives Set insertion and membership their own typed operations, with the Set slot and element as inputs. In the Field example, the write and the return each refer to their own value, so returning the saved read stays explicit. A read, write or assertion now has the same place in the model inside a branch as it does at the top level. The validator can reject a value used before its definition or incompatible branch results at the operation that introduces the problem. In the integrated design, a shared semantic fold walks the admitted operations for native and recorded execution.

What “algebra” means in this compiler

An algebra supplies a vocabulary of operations and rules for combining them. In this compiler, the vocabulary includes typed reads, writes, arithmetic, assertions, witness calls and control flow. The composition rules say which values are in scope, what each operation accepts and returns, and how a block produces its result.

The earlier shape recognizer answers “Does this whole circuit fit a recipe I know?” The algebraic model answers a series of smaller questions. Is this read legal for this declared slot? Does this value have the type the write expects? Do both branches produce a compatible result? Can the selected target represent the complete composition?

The syntax tree emitted at the end is a separate layer. A Rust AST represents the Rust expression or statement. The checked operation program represents the Compact behavior that expression must implement.

Concept Responsibility Example

Typed composition Connect the result of one operation to later operations Read the old Field, write the new Field, return the old one.

Effect composition preserves the source order. A write before a witness call can change the witness’s observation. Errors, gas, private state and the public trace also depend on order.

From two known pieces to a new composition

Suppose the compiler understands Field reads and writes and a typed conditional. We want to replace the stored value only when the caller selects that branch, while always returning the value from before the call.

The following Compact source illustrates that composition. Its admission depends on the compiler revision’s support for the listed operations and result types.

export circuit replaceIf(
  update: Boolean,
  next: Field
): Field {
  const before = state.read();
  if (disclose(update)) {
    state.write(disclose(next));
  }
  return before;
}

A recognizer built for the straight-line replaceValue shape can fail to match this conditional form. Extending the recipe catalogue would require checking a broader shape or adding another recognizer. Knowing the individual read and write operations alone gives that catalogue no general composition rule.

In the checked operation model, the value read at the start stays in scope through the conditional. Each branch has a Unit result, and the enclosing block returns the original Field.

Illustrative typed plan

before : Field = CellRead(state)
_ : Unit = If(update,
    then:
        _ : Unit = CellWrite(state, next)
        return Unit
    otherwise:
        return Unit)
return before

Starting from state 4, update = true and next = 9 leaves state 9 and returns 4. With update = false, the state stays 4 and the result is still 4. The chosen branch controls the write, and the outer result keeps its own identity.

How capabilities change

Question Whole-shape recognition Checked operation composition
What is the unit of reuse? A recipe for a recognized circuit family. A typed operation together with its composition and target rules.
What happens when a write moves into a branch? The new arrangement must match a supported recipe. The branch and nested write are checked as part of one plan.
How is a new primitive added? Update the relevant recipe families and their checks. Add its representation, validation, lowering and execution behavior, then qualify its permitted compositions.
Where can an unsupported case be explained? At the rejected shape or the narrower checks implemented by that recognizer. At the unsupported operation, type, boundary or resource constraint.
What establishes proof support? The applicable generated APIs and selected proof tests. The applicable generated APIs and selected proof tests. Proof verification and ledger acceptance require their own executed checks.

Support is also specific to types and boundaries. A Map can support structural membership or removal while lookup and write need an element codec. A collection being present in the model therefore does not make every operation on every element type available.

A new primitive still needs work. Adding its name to an enum is only the first step. The frontend must preserve its meaning, the checker must validate operands, and the runtime must execute the corresponding ledger behavior. Native and recorded adapters must agree about result, effects and ordering.

The benefit is that ordinary combinations can share those definitions. The compiler can grow through supported operations and explicit composition rules instead of accumulating a separate recipe for every useful arrangement.

Porting the cryptographic surface

A curve name is only the beginning

Supporting P-256 or secp256k1 means more than exposing a verification function. The compiler needs source types, defaults, casts and operations. Generated Rust needs distinct carriers. Fields before points

Base and scalar fields have different moduli. Rust types preserve that distinction, so an ordinary call cannot accidentally substitute one carrier for another. Explicit source casts have their defined modular behavior. An untrusted host decoder still needs a canonicality check.

Foreign field ledger transport also uses shifted values and split atoms. For the selected K1 and P-256 layouts, the low and high parts occupy 24 and 8 bytes. A plain integer comparison would miss a representation error.

Technical guide

A proof is one stage

Follow one circuit all the way

The pipeline explorer shows eight stages. Each stage has an owner, a useful output and a failure that the next stage can expose.

Source admission

The frontend checks Compact syntax, types, disclosure and supported target capabilities. A newer language pragma may fail before a circuit is considered. A derivative with that pragma removed is useful for investigating semantics, with its changed source identity recorded explicitly.

Typed lowering and Rust emission

The internal IR preserves types and operations, and carries source origins where the frontend supplies them. Checked lowering establishes a Rust representation and legal control flow. Syntax emission renders the admitted model. Generated code compilation catches Rust-level errors in the public API. Structural and type checks do not establish source semantic equivalence. A same-typed operand or slot substitution needs an independent behavioral observation.

Native execution

Execute the generated function against the selected ledger runtime. Compare returns, state, witnesses, private state and gas with an independent reference case.

Recorded execution and replay

Record the same admitted effects and replay them through the ledger VM. Compare the resulting state and ordered observations. Losing a Unit-valued effect can be detected here even when the return value looks harmless.

SDK preflight

Interpret the exact ZKIR against the serialized preimage. Check its raw identities and compare input, output, public transcript and private transcript fields. Mutated statements should be refused when they violate the original circuit.

Fresh standalone proof and verification

Generate the selected keys from pinned parameters and exact IR. Produce a new proof. Verify in an independent process with the verifier rederived from those identities. Exercise wrong-verifier, changed-binding and corrupt-proof controls.

Funded transaction

Construct a separate transaction-bound proof. Preserve the observed installed operation. Include genuine fee funding and default-strict ledger verification. Compare the applied state and events to generated native execution.

Replay and rollback

Apply the same verified transaction again. The accepted result in the selected lanes is IntentAlreadyExists with unchanged whole-ledger bytes and no repeated events. A broader transaction failure may also require rollback tests.

Why syntax trees mattered

syn does not prove that generated code is semantically correct. What it does is move an important class of failure earlier: output is constructed as Rust syntax rather than assembled as strings. quote and proc-macro2 make larger fragments composable; prettyplease makes the resulting syntax readable and deterministic.

The stronger guarantee comes from the surrounding discipline:

  • the IR enums are closed and reject unknown fields;
  • types, actions and expressions have explicit variants;
  • resource preflight bounds depth, nodes and call expansion;
  • malformed IR is an error, while unsupported recording is a typed capability outcome;
  • generated fixtures compile and execute; snapshots alone are not acceptance.

1. Compact declares meaning

examples/rust_backend/tiny_oracle.compact declares a small state machine:

enum STATE { unset, set }

ledger authority: Bytes<32>;
export ledger value: Field;
ledger state: STATE;

witness private$secret_key(): Bytes<32>;

circuit set(v: Field): [] {
  assert(in_state(STATE.unset), "set: attempted to overwrite recorded value");
  const sk = private$secret_key();
  authority = public_key(sk);
  value = disclose(v);
  state = STATE.set;
}

circuit get(): Maybe<Field> {
  return in_state(STATE.set) ? some<Field>(value) : none<Field>();
}

Compact owns source typing, disclosure rules, witness declarations, circuit control flow and ledger declarations. None of those rules should be inferred from a Rust string template.

2. Generated types use mechanical derives

The generated library tests-rust-backend/tiny-oracle/lib.rs turns the source enum and product into ordinary Rust types:

#[derive(Clone, Debug, Default, PartialEq, Eq,
         runtime::CompactCellValue, runtime::CompactStructRepr)]
pub struct Maybe {
    pub is_some: bool,
    pub value: runtime::Field,
}

#[derive(Clone, Copy, Debug, PartialEq, Eq,
         runtime::CompactCellValue, runtime::CompactEnum)]
pub enum STATE { unset, set }

The macros implement only mechanical representation rules: FAB alignment, Cell conversion, field/binary representation and checked enum ordinals. They do not interpret circuit bodies.

3. Ledger declarations become typed slots

pub const authority: runtime::slots::CellSlot<runtime::FixedBytes<32>> =
    runtime::slots::CellSlot::new(&[0]);
pub const value: runtime::slots::CellSlot<runtime::Field> =
    runtime::slots::CellSlot::new(&[1]);
pub const state: runtime::slots::CellSlot<crate::types::STATE> =
    runtime::slots::CellSlot::new(&[2]);

A slot binds the source declaration's value type to its physical ledger path. Generated code asks the slot to read, write, inspect or record. The runtime owns the canonical ledger-8 VM program for that operation.

4. Native Rust makes order and cost visible

The generated set function is ordinary fallible Rust. A simplified excerpt:

let prior = in_state(context, STATE::unset)?;
context = prior.context;
total_cost += prior.gas_cost;
if !prior.result {
    return Err(runtime::CompactError::AssertionFailed(
        "set: attempted to overwrite recorded value".to_owned(),
    ));
}

let meter = runtime::context::WitnessReadMeter::new(&context);
let (next_private, sk) = witnesses.private_secret_key(
    context.witness_context_with(LedgerView {
        state: context.query.state.get_ref(),
        meter: &meter,
    }),
)?;
total_cost += meter.gas_cost();
context.private_state = next_private;

let step = ledger_slots::authority.write(context, public_key(sk)?)?;
let context = step.context;
total_cost += step.gas_cost;

The successor context is consumed and returned. Query costs are accumulated in source order. Witness ledger reads are metered without making private witness values part of the public verification program.

5. Recording uses the same domain operations

Where the complete circuit is admitted, the generator also emits a recorded path:

let frame = runtime::recording::RecordingFrame::new(context);
let (frame, prior) = ledger_slots::state.record_read(frame)?;
if prior != STATE::unset {
    return Err(runtime::CompactError::AssertionFailed(
        "set: attempted to overwrite recorded value".to_owned(),
    ));
}
let (frame, sk) = frame.try_witness_metered(|context, meter| {
    witnesses.private_secret_key(
        context.witness_context_with(LedgerView {
            state: context.query.state.get_ref(), meter,
        }),
    )
})?;
let frame = ledger_slots::authority.record_write(frame, public_key(sk)?)?;
let frame = ledger_slots::value.record_write(frame, v)?;
let frame = ledger_slots::state.record_write(frame, STATE::set)?;
Ok(frame.finish(()))

The native execution result and replayable public trace remain distinct inside RecordedCircuitResult. Recording support is emitted only when every required operation has a checked recorded form.

6. The consumer sees a smaller facade

The generated crate exposes native methods, a borrowed recording handle when witnesses are needed, and—with the transaction feature—typed observed-call builders. The consumer supplies private state, witnesses, observed public state and exact verifier artifacts; generated code preserves the Compact entry point and typed public input.

let native = contract.set(context, value)?;
let recorded = contract.recording().set(context, value)?;
let call = contract.recording().set_call(&observed, private, value)?;
let prototype = call.prepare(verifier, commitment_randomness)?;

These three lines do not make equivalent claims. The first executes natively, the second also produces a trace, and the third binds that trace to an observed contract and verifier before ledger preparation.

7. Preparation does not hide the prover

A proof-capable consumer continues explicitly from the generated *_call builder. The exact provider API depends on the integration harness, but the ownership boundary remains visible:

let call = contract
    .recording()
    .commit_call(&observed, private_state, value)?;

let prepared = call.prepare(verifier, Fr::from(0_u64))?;

let intent = Intent::empty(&mut rng, expiry)
    .add_call::<ProofPreimage>(prepared);

let transaction = Transaction::from_intents(
    "local-test",
    HashMap::new().insert(1_u16, intent),
);

    .prove(
        provider,
        &INITIAL_PARAMETERS.cost_model.runtime_cost_model,

    .await?;

The generated call builder knows the typed entry point and public input. The consumer supplies the observation, verifier artifact, commitment randomness, provider and transaction policy. A successful prepare therefore does not claim that proving or ledger application has succeeded.

  • Private witness outputs and public verifying operations are separate.
  • Gas is observed from executed queries rather than guessed in the emitter.

The backend became more trustworthy by moving failures to the earliest layer that has enough information to explain them—without pretending every failure can happen at compile time.

The gas-accounting correction

The original comparison looked alarming: Rust reported much more gas than the TypeScript wrapper for the same tiny circuit. The implementations were not using the same reporting denominator.

TypeScript replaced context.gasCost after each query and exposed the last query. Generated Rust accumulated every query. The accepted decision in RUST-ADR-0010 kept the Rust total and changed the comparison to the sum of captured TypeScript query costs. For clear, set and get, all four dimensions then matched exactly at commit test(rust-backend): pin tiny per-query gas parity .

reported TS wrapper cost       = last query only
captured TS comparison cost    = Σ every executed query
Rust CircuitResult.gas_cost    = Σ every executed query
transaction gas                = replay/partition result, separately owned

The four dimensions are read time, compute time, bytes written and bytes deleted. They should not be collapsed into one scalar.

Witness reads became visible

A witness could read a ledger Cell structurally while TypeScript executed a VM read. Rust therefore underreported the call. The explicit WitnessReadMeter introduced at feat(rust-runtime): meter witness ledger view reads charges canonical witness projection queries while keeping their private value out of the public trace. The Set extension followed at feat(rust-runtime): meter witness Set queries .

One witnessed Cell write moved from an incomplete Rust read-time total of 85,000,000 to the exact captured total of 255,000,000: 170,000,000 for the witness read plus 85,000,000 for the write. That is corrected accounting, not a cheaper VM operation.

Per-query guard, whole-circuit observation

At ledger-8, CircuitContext.gas_limit guards each query independently. A circuit containing two accepted reads may therefore report a total above the configured one-query limit. Commit docs(rust-backend): define per-query ledger gas limits made that contract explicit and tested. Silently turning it into a cumulative budget would diverge from the pinned TypeScript/ledger behavior and introduce new rollback questions.

Representative issues that were fixed

Invalid Rust became a source-located compiler error

Distinct Compact circuit names such as a$b and a_b normalize to the same Rust identifier. Before, rustc rejected a duplicated function after emission. Commit test(rust): strengthen semantic boundary coverage and declaration checks added target-namespace preflight and reports both source names at the later declaration. See RUST-ADR-0246.

Macro expansion stopped depending on caller names

Derives introduced unqualified Result, Option, Vec and From, so valid consumer names could break compilation. Commit fix(rust): qualify macro-owned names in consumer expansions fully qualified macro-owned names. Source structs named Option, Fr, MemWrite, runtime or FieldRepr exposed a second failure in upstream derive/import expansion; the owned CompactStructRepr boundary fixed the bounded generated shapes at fix(rust): isolate generated types from representation support names .

Forged recursive IR stopped becoming recursive Rust

The normal frontend rejected recursive Compact, but direct schema-20 IR could still emit recursive pure Rust. Commit fix(rust): reject recursive pure calls in private IR moved the refusal to private-IR semantic admission while preserving acyclic shared helpers. See RUST-ADR-0332.

Malformed ledger paths stopped panicking or truncating

Merkle/list reset builders used split_last().expect; other builders narrowed path lengths before constructing compact VM operands. Commit fix(rust): validate ledger VM path operands before lowering checks the actual 4-bit Ins/Idx encoding limits and returns the existing fallible ledger error rather than panicking, truncating or emitting an ambiguous program. See RUST-ADR-0351.

A truthful refusal replaced a misleading bounds error

Valid wide unsigned types could be represented, but subtraction, multiplication and ordered comparison were unsupported. They were incorrectly reported as malformed maxima. Commit fix(rust): distinguish unsupported wide integer operations added UnsupportedWideUnsignedOperation without widening accepted behavior. See RUST-ADR-0352.

The architectural rule

Move a failure earlier only when the earlier layer has authoritative facts. Source recursion and name collisions belong before Rust publication. An assertion depending on current ledger state remains a runtime Result. Verifier identity cannot be authenticated until preparation. Proof and ledger rejection must not be simulated by compiler heuristics.

The useful history is not a straight line. These are representative moments where the evidence changed the architecture or narrowed a claim.

1. Preserve the old backend instead of deleting it

Problem. A clean rewrite could regress behavior while making comparison impossible.

Decision. Keep codegen-rust as an oracle and compare exact sources, results, state, transcripts and refusals.

Evidence. The first Rust-AST milestone ran all 37 exact top-level oracle sources through the new path.

Benefit. The project could change the architecture without rewriting its own history.

Limit. An oracle can contain defects; agreement is evidence, not truth.

2. Use a closed IR, not a Rust-source escape hatch

Problem. Text fragments let unsupported source shapes leak into output and made exhaustive review difficult.

Decision. Model Compact types, expressions, actions and returns as strict serde variants and reject unknown input.

Evidence. Compiler-backed refusal probes, fixture regeneration and external Cargo consumers accompanied schema changes.

Benefit. New constructs require an explicit compiler/backend decision.

Limit. The private schema still couples the Chez producer and Rust consumer; its version is not a public language specification.

3. Generated syntax is necessary, not sufficient

Problem. syn guarantees parseable Rust construction, but semantic bugs can still live inside valid syntax.

Decision. Keep AST construction and add execution, independent expected values, TypeScript observations, negative controls, replay and proof gates.

Evidence. Field modular arithmetic, Boolean witness order, source-defined returns and output-recovery tests caught stale or overly textual assumptions.

Benefit. Generated code is checked as a program, not a string.

Limit. Hundreds of substring assertions remain useful smoke tests but are not semantic proof.

4. The point type was too “safe”

Problem. Rust represented Compact JubjubPoint as a validated subgroup point. Compact's source value is a coordinate pair, and the upstream constructor could panic on some invalid/subgroup-external coordinates.

Decision. Separate source representation from checked operation admission; validate only where an operation requires a real point.

Evidence. Cross-language parity tests reproduced the divergent values and panic boundary.

Benefit. Rust no longer changes source representation under the banner of type safety.

Limit. A checked backend may still deliberately refuse behavior that the reference path accepts; that difference must be documented, not hidden.

5. Shape recognizers reached their ceiling

Problem. Every useful application family added another whole-program admission profile. Supported operations did not compose automatically.

Decision. Introduce a typed RecordedPlan, migrate one family at a time, and retain the old paths as differential oracles until retirement evidence exists.

Evidence. Per-family default/feature tests, generated-source inventories, source-bound proof/application cases and an explicit retirement ledger.

Benefit. The unit of reuse becomes an operation plus its invariants.

Limit. A compositional IR can centralize bugs too; exhaustive variants, resource limits and old-first laws remain necessary.

6. Full Passport ACC adoption was the wrong milestone goal

Problem. A large ledger9-era application risked turning unrelated foreign curve, WebAuthn and newer-ledger requirements into alleged ledger-8 support.

Decision. Inventory constructs, retain generic Jubjub work, remove full ACC adoption and keep bounded passport/DID cohorts separately evidenced.

Evidence. The 0.3 closure records the removed outcome and the exact retained application cases.

Benefit. Useful compiler work survived without a misleading product claim.

Limit. The bounded passport cohort is not the full ACC application.

7. A faster test gate may not skip authentication

Problem. Historical validation took about 171 minutes, more than 99% in historical checks. Naive memoization would have hidden live mutation.

Decision. Reject path/result caches and shard whole modules into isolated processes, preserving fixture boundaries and independent temporary state.

Evidence. All 974 IDs and assertions remained; corruption and source mutation controls passed; measured wall time fell to about 55 minutes.

Benefit. Faster feedback without turning a historical assurance suite into a snapshot replay.

Limit. The result is machine/source specific and still needs the full gate at final freeze.

8. Source provenance must be honest

Problem. Hand-built IR can make a backend look more source-compatible than the frontend actually is, while absolute paths and private artifacts are unsafe to publish.

Decision. Authenticate source, IR and artifact sidecars; distinguish original occurrences, owned snapshots and missing origins; carry safe logical source identity and structural paths.

Evidence. Authenticated input views, original-source guards and publication manifests preserve exact hashes and failure cases.

Benefit. A passing fixture can be tied back to a real Compact source.

Limit. Nested expression ranges and transient-value provenance are not claimed implemented at this cutoff.

Independent review boundary

The project used independent coding-agent reviews for architecture, dependency, correctness and final-slice checks. They found actionable issues and provided a useful second model. They are not a human security audit, formal verification or production certification. The story uses the exact phrase “independent coding-agent review” for that reason.

FAB / aligned value The field-aligned binary/value representation used across Compact values, witness transcripts and ledger/proof boundaries.

Native execution Running a generated circuit against the Rust runtime to obtain a result and updated context. It does not imply recording or proof support.

Recording Producing the ordered public VM/effect program and private/public values needed for replay and later proof-oriented integration.

Replay Checking a recorded program against observed state and runtime invariants.

Preparation Constructing a ledger call/prototype from recorded execution, observed state, verifier material and caller-supplied policy.

Proof applicability Whether a circuit and its exact artifacts have the required public/private inputs and policy to be proved. A generated recording API is not enough.

Shape recognizer / recording profile A specialized admission path that recognizes a known whole-circuit pattern. It was useful for early coverage but did not compose naturally.

Recording effect algebra The prototype's typed vocabulary and composition rules for building a complete RecordedPlan from checked operations.

Typed refusal / RecordingGap A structured explanation that native code may exist while a complete recorded path does not. It carries a stable code, node, structural path and detail.

Oracle An independent implementation or captured output used for comparison. Oracles are evidence and can themselves contain bugs.

Old-first law A migration check that asks the legacy implementation first, then ensures the new path preserves accepted/refused behavior and takes ownership deliberately.
